# 在 Telegram 内充值和购买广告

2026-11-19，Go + MySQL 增量实现。用户无需跳转网站，网站与机器人继续使用同一用户、余额、充值订单、广告订单和审核规则。

## 用户入口

| 私聊命令 | 功能 |
| --- | --- |
| `/account` | 钱包首页：余额、充值、广告、订单、资金明细 |
| `/wallet` | 恢复当前填写或查看钱包；会话有效期 30 分钟 |
| `/recharge` | 选择已启用的充值方式，输入金额，确认生成订单 |
| `/ads` | 选择已开放广告位，填写广告并确认购买 |
| `/cancel` | 清除未提交的填写内容，不撤销已经创建的订单 |
| `/login` | 主动生成网站一次性登录码，网站是可选入口 |

`/start` 中已有「我的」「用户中心」「商业中心」动作直接进入机器人内钱包。群里的 `/ads` 仍是群广告拦截管理命令；财务操作仅限本人私聊。

### 按聊天场景区分入口

- 私聊命令菜单包含搜索、收录、账户、钱包、充值、广告购买及主动 `/login`；不显示群管理命令。
- 普通群成员的菜单仅包含 `/start`、`/search`、`/discover`、`/help`；群里的 `/start`、`/help` 只返回搜索说明，不带个人菜单。
- 群管理员在搜索命令之外，可见搜索验证、新人验证、消息字数、欢迎语、广告/媒体/转发拦截、防刷屏等群管理命令。每次执行仍实时验证管理员身份。
- 使用 Telegram `default`、`all_private_chats`、`all_group_chats`、`all_chat_administrators` 四种 scope 注册。默认菜单也仅含搜索帮助，覆盖旧的混合命令列表；启动和切换 Bot 后同步，失败自动重试并记录 `commands_state`、`commands_error`。
- 手动在群里输入个人命令会被服务端忽略，不能修改私聊中的填写状态；转发或残留的个人菜单、钱包按钮在群中只弹出拒绝提示。

钱包首页的账户 ID 显示当前用户的 **Telegram ID**，文案统一为「账户 ID：」，不附加平台名称；身份查询继续使用绑定的 `telegram_id`，资金表内部关联仍使用用户主键。「我的」不再显示网站登录按钮或网站引导；旧的 `website` 按钮刷新为新版钱包，不生成登录码。主动私聊 `/login` 和网站发起的 Telegram 绑定/登录保留，登录码消息也使用相同的账户 ID 文案。

## 充值

1. 选择 USDT-TRC20 或线下转账，输入 1–100000 USDT。
2. 确认后生成订单。TRC20 输入整数，订单分配六位小数准确付款金额，显示完整收款地址和截止时间；用户自行通过钱包转账。
3. TRC20 可点击「核查到账」或提交 64 位交易哈希。与网站复用 Tronscan 核验，不根据截图或用户声称付款入账。付款窗口已结束时不再展示付款引导；有效期内发出的交易仍可查询。
4. 线下转账可在机器人发送 5–500 字说明，或 JPEG、PNG、WebP 截图（最多 5 MB、1200 万像素）。图片重新编码为 PNG，去掉元信息；截图库独立于订单表，不暴露 Telegram file ID、下载地址或 Token。
5. 提交凭证进入后台审核，不能直接增加余额。已按时提交的订单可在付款截止后继续审核，但不能超时补交或替换凭证。

后台充值设置决定哪些方式可用；停用方式在机器人中不会显示。订单页、充值历史和资金明细随查询读取最新状态。当前通过「刷新订单」查询审批/到账结果，没有额外推送通知任务。

截图保存在 `ts_recharge_proofs` 私有表，单订单一张，事务内原子替换。只有订单所属用户，或拥有 `recharges.read` 且可读 `proof` 字段的管理员，可调用受保护的图片接口。后台与用户中心提供按需预览、加载失败重试和关闭回收；响应 `private, no-store`。后期图片量增大可迁移到私有对象存储，保持接口和权限边界不变。

## 广告购买

1. 广告目录每页 5 个，只展示已启用的广告位。
2. 查看广告类型、固定价格、投放天数和目标；逐步填写标题、HTTPS 链接、可选正文，以及关键词/品牌词。
3. 预览完整内容与扣款金额。点击「确认购买并扣款」后，由既有 `BuyAd` 服务事务扣除余额并生成待审订单。
4. 事务重新校验账号及 Telegram 绑定、报价、投放天数、广告位名称/类型/目标、容量和余额。报价变化需要点击「刷新报价」并再次确认。
5. 余额不足可进入充值，广告草稿保留；到账后「继续购买广告」恢复草稿。审核通过后开始计时，拒绝退回余额。已提交订单可在机器人直接查状态、审核说明和投放时段。

价格和期限由广告位配置决定。此功能不会开放原本停用的广告位，也不会自动批准广告。

## 聊天整洁与消息保留

私聊导航共用一个临时页面。按钮操作优先原地编辑；文字命令打开新页面时，先确认新页面发送成功，再删除上一个临时页面及本次已经消费的普通命令。填写步骤同样遵循这一顺序，发送失败时保留原提示和输入。

| 消息类型 | 处理方式 |
| --- | --- |
| 主菜单、帮助、账户页、充值与广告填写提示、空 `/add` 或 `/search` 提示 | 只保留最新临时页面 |
| 普通导航命令、已通过校验的充值金额及广告填写文字 | 成功进入下一步后清理 |
| 校验失败或发送失败时的输入 | 保留，方便检查和重试 |
| 搜索关键词、搜索结果及收录回执 | 保留，成功返回结果后退出旧临时导航 |
| 充值订单、广告订单结果 | 保留；重新打开同一订单时更新原回执，返回菜单不覆盖回执 |
| 付款说明、凭证图片及交易哈希 | 保留 |
| 独立网站登录与验证信息 | 保留，继续遵守原有有效期 |
| 群成员消息、群搜索记录与更新前未跟踪的历史消息 | 不参与本次清理 |

`/help` 与返回主菜单一样，会暂停当前钱包填写，防止提示已经切换、普通聊天却继续被当作表单内容。广告草稿仍可通过 `/wallet` 恢复。此轮沿用既有图标和按钮布局，采用 `ui-ux-pro-max` 的状态保留与返回导航原则。

新增 `012_bot_chat_cleanup.sql`，仅创建 `ts_bot_chat_views` 和 `ts_bot_message_cleanup` 两张表。跟踪键包含机器人、本人私聊与页面/订单标识，重启后可以继续清理。按机器人和私聊串行投递，未注册的历史消息不会被接管。

清理与业务结果分开处理：每次成功处理更新后及长轮询前最多尝试 8 条，单轮预算 3 秒。网络错误进入持久队列，最多尝试 6 次；限流遵守 `retry_after`。消息不存在或无权删除等不可恢复错误结束该项清理，不重复充值、扣款或购买。实际调用前再次保护当前页面和保留的订单回执，切换 Bot Token 后也不会使用新机器人的凭据处理旧机器人消息。

只为创建不满 47 小时的消息安排删除，以避开 Telegram 的删除时限。超过期限放弃清理；72 小时不再更新的页面跟踪元数据可以移除，这不会删除真实订单消息。此功能不扫描或批量清空旧聊天历史，也不改变后台业务记录。

## 状态与并发

- 新增 `010_bot_commerce.sql`、`011_commerce_proofs.sql` 和 `012_bot_chat_cleanup.sql`；迁移只增加表，不重建用户、钱包或历史订单。
- `ts_bot_commerce_sessions` 持久保存状态、草稿、版本、消息 ID 与最后消费的输入 ID。一个机器人/Telegram 用户只有一个当前会话，绑定网站用户和私聊。
- 按机器人/用户用 MySQL advisory lock 串行化一次操作；进程最多 4 个钱包操作同时进入，以保留资金事务的数据库连接。忙时提示稍后重试，不排入无限队列。
- 钱包操作的数据库事务不会跨 Telegram 网络调用；确定的请求键先随草稿保存，再提交充值/广告服务。
- 老版本、错误消息、其他用户、其他机器人和群聊按钮均不能操作当前会话；报价变化或停用账号不会扣款。后台绑定变更在资金事务中再次核对。
- 资金提交成功但 Telegram 发送失败，不再次扣款。用户发送 `/wallet` 可恢复已提交订单；重放已消费的文本不会进入普通搜索。
- 验证码答案优先处理，财务填写不抢验证码输入。显式搜索、提交收录或返回主菜单会离开当前填写状态；广告草稿可从钱包恢复。
- 钱包草稿 30 分钟不操作即失效；超过 7 天的过期会话按每轮最多 1000 行清理，资金订单独立保留。

这适合当前单实例/少量实例。没有将机器人轮询改造成高并发队列；未来可把交易状态机迁入按用户分区的消费者，保留订单幂等键、事务和唯一约束。
